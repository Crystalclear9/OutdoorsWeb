# 运行与维护

## 长期运行与维护

超级管理员可在“运行维护”查看数据库和磁盘检查、最近成功备份、维护失败信息及超时待办，并手动启动一次后台备份和清理。普通企业及工作人员不能使用维护 API。

- 服务启动约 10 秒后执行首次维护，随后每小时检查一次。默认约每 24 小时备份，保留最近 14 份自动备份；`BACKUP_INTERVAL_HOURS`、`BACKUP_KEEP` 可调整，间隔设为 0 仅关闭自动备份，仍进行清理和手动备份。
- 备份在独立 Node 进程中执行，先写 `.part` 文件，完成 `PRAGMA quick_check` 和密钥准备后才发布为正式备份，并记录成功时间。只轮换本程序生成的 `auto-*.sqlite`，保留数量最少为 2；不会轮换人工命名的备份。失败保留诊断，并输出结构化错误日志。
- 自动备份先准备临时数据库和密钥，再不覆盖地发布配对文件；密钥写入失败不留下假正式快照。轮换先从新到旧检查完整文件配对和数据库完整性，确认足够保留份数才删除更旧配对；孤立文件、坏密钥及检查中发现的坏库不占保留名额，保留供运维核查。更旧未扫描配对按文件与密钥基本条件及文件身份检查后轮换，不代表每份都完成恢复验收。默认 14 份的检查在维护子进程执行；调高至 365 份或大库时须评估读盘成本。过期临时密钥侧车与数据库临时文件只按受控名称清理。
- 维护页同时核对最近备份文件是否存在；文件丢失或为空会提示异常，并在下次已启用的自动维护中重新生成。复制前检查备份目录可用空间，预留数据库估算大小及安全余量，避免已知空间不足时继续复制。
- 默认目录 `/app/data/backups` 随 Docker 数据卷保留。**这仍是本机备份**，请通过运维任务复制到异机或其他独立存储；已实现 S3 兼容加密异机复制及签名 Webhook 告警，配置及验收见[外部服务接入](integrations.md)。
- 定期清理过期验证码、过期会话、过期超过一天的限流记录、超过 7 天的幂等标识，以及超过 180 天的已读消息。预约与账号保留。默认超过 365 天的非待审申请设计图及历史审计日志分批完整归档；设计图仍在原申请按权限读取，审计归档在“操作日志”下载 JSONL，读取时校验 SHA-256。
- 设计图仍存于 SQLite；单个企业未归档设计图限制为 200 MB。归档保留在同一个 SQLite 快照中，保证恢复时资料齐全；这是冷热分层，保留的数据仍占用磁盘。新库启用增量空间回收，每次维护最多回收 1024 个空闲页；旧库可离线压缩并启用后续增量回收，见下文。空间回收不删除保留的历史资料，仍需容量规划。`ARCHIVE_AFTER_DAYS` 可设为 30–3650 天，每次维护最多归档 20 张历史图片及 2000 条旧日志。磁盘可用空间低于 `MIN_FREE_DISK_MB`（默认 256 MB）时，健康检查失败并阻止继续提交申请；不能代替磁盘容量规划。
- `/api/health` 检查数据库写入能力及磁盘空间，异常返回 503，不公开内部路径。反向代理或外部监控可检测这个地址；Docker Compose 的应用日志限制为每份 10 MB、最多 3 份。健康失败不会自动等同于完成修复，需要维护人员处理。
- 异常请求日志含 `X-Request-ID` 对应编号，方便定位；不输出请求正文和密码。界面中的维护状态与站内消息不能代替独立于应用的故障告警。

反向代理部署时，将 **直接连接应用、且确实由你控制的代理 IP** 填入 `TRUSTED_PROXY_IPS`（逗号分隔），代理应正确覆盖或追加 `X-Forwarded-For`。程序从右向左跳过可信代理，取第一个非可信地址；未配置时忽略所有转发头。不要信任任意用户能控制的代理或整个公网，否则会破坏限流。代理容器更换 IP 后，应同步更新配置。

维护取得租约、启动子进程或释放租约失败时返回失败结果，不让定时任务的同步异常导致服务退出。数据库忙到无法保存失败状态时，仍输出结构化错误到标准错误；此时维护页面可能保留旧状态，应结合容器日志及独立监控检查。释放失败会保留带到期时间的租约，避免立即重复执行；排除锁定后可在租约到期后重试。通信任务保存失败信息时也有独立日志兜底，服务商是否受理仍须核实，不能盲目重发。

升级通知重试修正前先备份并停止旧版本进程。新版本启动时，旧通信适配器留下的 HTTP 5xx/408 或缺失受理编号的待重试/失败任务会转为“需核实”，递增版本并保留原错误审计；已经人工核实的结论不变。升级后在“运行维护”检查这些任务，到服务商核对后再关闭或重试，不要直接修改数据库绕过核实。新响应的分类与限流等待规则见[外部服务接入](integrations.md)。

## 工作日历与电话跟进

维护任务按日历检查超过一个工作日且未登记结果电话告知的申请，包括已审批但未告知的记录；每天最多提醒审核人员一次。日历维护、财务授权、取消核款和升级到版本 7 的说明见[办理指南](casework.md)。实际拨号、资金核对及超时处置需要人员负责，自动任务不会代替审批、收费或退款。

新申报及改期复制设计图均受磁盘健康阈值限制；存储异常时返回 503，改期失败不会取消原预约或新增半条申请。排除存储问题后再重试，不要以删除持久卷处理空间不足。

## 管理员恢复与备份

管理员在首次启动时创建，后续更改环境变量不会自动覆盖已设置的密码。忘记管理员密码时，先修改 `.env` 的管理员配置，再显式执行：

```powershell
docker compose run --rm app node server/admin.mjs
```

该操作更新管理员密码并撤销其全部会话，不会把已注册企业提升为管理员。非 Docker 环境执行 `npm run admin:recover`。验证器与全部恢复码同时遗失时，仅由有服务器权限的运维显式执行 `node server/admin.mjs --reset-mfa`（或 `npm run admin:recover -- --reset-mfa`），重置后管理员必须重新扫码。普通密码恢复不会移除 MFA。

在线一致性备份：

```powershell
docker compose exec app node server/backup.mjs /app/data/backups/manual.sqlite
docker compose cp app:/app/data/backups/manual.sqlite ./backup.sqlite
docker compose cp app:/app/data/backups/manual.sqlite.mfa-key ./backup.sqlite.mfa-key
```

备份使用 SQLite `VACUUM INTO`，包含账号、申请、图片、归档及通知队列。旁边的 `.mfa-key` 也必须保管，恢复时作为数据库同目录的 `.mfa-key`；使用 `APP_ENCRYPTION_KEY` 时保留同一密钥。备份和密钥均为敏感资料，限制访问。目标文件必须尚不存在，每次备份请更换文件名。不要仅复制运行中的 SQLite 主文件，WAL 中可能仍有未合并数据。

手动备份在复制前检查密钥格式，临时数据库执行 `quick_check` 后，还须用配套密钥验证快照内全部 MFA 密文的 AES-GCM 认证标签，再以不覆盖已有目标的方式发布。自动备份、压缩安全快照、异机上传和加密恢复采用相同校验；没有 MFA 表或记录的旧库仍兼容。不输出验证过程中解密的秘密。

32 字节长度正确不等于密钥可用。最近备份失配时不能据此跳过应补做的备份；自动轮换也只把实际校验通过的配对计入保留数量，损坏配对保留供调查，不挤掉其余可恢复备份。维护页显示的是历史备份结果与当前文件元数据，不能替代实际恢复演练。独立快照上传异机时使用快照自己的 `.mfa-key`，不以当前应用密钥替代。若当前应用密钥已经损坏，程序会明确失败，须找回匹配密钥；校验不会自动修复丢失的密钥。

恢复前先停止应用并备份原卷。由运维人员通过临时容器替换卷内数据库，并处理相应 WAL/SHM 文件后再启动。不要将任何业务数据库提交到仓库。

加密恢复必须使用新的空目录。数据库正式发布失败时，仅撤销本次新建且文件标识仍匹配的目录密钥，已有密钥及恢复期间被其他进程替换的文件保留，目标数据库也不会覆盖。失败后仍须检查目录和错误原因，不要把正在运行的业务目录作为恢复目标。

### 旧库离线压缩与空间回收

在维护窗口先停止应用，再执行以下命令。程序会先检查数据库及临时磁盘空间，生成 `precompact-*.sqlite` 安全快照和 MFA 密钥副本，校验成功后才重建数据库并启用增量回收；不删除预约、图片、账号或历史归档。保留安全快照直到确认运行正常。大库需预留额外空间，空间不足会拒绝执行。

```powershell
docker compose stop app
docker compose run --rm app node server/compact.mjs --offline
docker compose up -d
```

非 Docker 环境停止 Node 服务后运行 `npm run compact -- --offline`。维护页显示已分配空间、可复用空间以及是否启用增量回收。依据 [SQLite 空间回收机制](https://www.sqlite.org/pragma.html#pragma_auto_vacuum)，旧库由 NONE 模式切换需一次 VACUUM；程序不会在升级启动时自动执行可能长时间阻塞的大库重建。

## 升级与回滚

升级前先生成并复制一份一致性备份及 MFA 密钥，记录当前提交和镜像。确认工作目录没有未保存的本地修改，再更新：

```sh
git pull --ff-only
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 app
```

启动会执行增量迁移。当前数据库结构版本为 7，旧版手机号绑定验证码需要重新获取，既有预约补齐电话跟进状态但不推定已经告知。更新后核对登录、申请查询和审批、公告、办理与费用记录、最近备份及维护状态。不要删除持久卷来解决启动问题。完整交接项目见[上线与运行验收清单](release-checklist.md)。

回滚前停止应用并备份当前数据。程序和数据库必须匹配；不要直接将不理解当前结构的旧镜像连接到新库。隔离恢复旧快照、验证账号、设计图和 MFA 后再切换。使用 `APP_ENCRYPTION_KEY` 时必须保留对应的原密钥。加密备份恢复步骤见[接入指南](integrations.md#加密异机备份恢复与独立告警)。

## 常见问题

| 现象                         | 核对与处理                                                             |
| ---------------------------- | ---------------------------------------------------------------------- |
| Pages 可打开但账号服务未连接 | Pages 是静态入口，使用 Docker 完整服务地址；不要把静态预览当作完整服务 |
| 启动提示管理员配置无效       | 替换 `.env` 的示例密码；已有账号改密码须走恢复命令                     |
| 管理员无法进入业务页面       | 按账号设置完成临时密码修改和两步验证，核对职责授权                     |
| HTTP 本地登录后会话无法保存  | 本地 HTTP 使用 `COOKIE_SECURE=false`；HTTPS 正式环境使用 `true`        |
| 返回 403 来源或安全校验错误  | 核对访问域名、`PUBLIC_ORIGIN` 与代理配置，刷新会话；不要关闭 CSRF 校验 |
| 返回 409                     | 记录版本、审批状态或占用已经变化，刷新后核对再处理                     |
| 返回 429                     | 登录或业务限流已触发，等待对应窗口结束                                 |
| 返回 503                     | 核对数据库锁、磁盘阈值、认证队列或外部服务；结合请求编号和日志定位     |
| 磁盘占用没有随归档下降       | 归档保留资料；检查可复用页、容量及离线压缩条件                         |
| 通知显示“需核实”             | 到服务商后台核对是否已受理，再在维护页面处理，避免重复呼叫             |
